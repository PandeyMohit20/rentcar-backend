# Complete the pending global billing approval

**GST registration update:** use the [conditional policy guide](gst-registration-policy.md). Explicit REGISTERED/UNREGISTERED replaces the old unconditional GSTIN assumption. The unaudited operator CLI no longer writes policies. Authenticated profile edits may reopen prior approval; status changes require a new version and old/new status audit. Historical invoice snapshots are not migrated.

This is an administrative completion workflow, not authority to select GST or CESS rates. Never use test fixture values as business approval. The existing quote gate and tax calculation are unchanged.

## Scope and prerequisite

`billing.issuer.phase7b.pending` blocks quotes globally, even when `isActive=false`. Completing it for just one car could expose other cars with unconfigured taxation in development. Completion therefore reviews **all non-deleted cars**, their vendors, and every active rental-pricing record. Currently the live database contains 15 cars, one vendor, and 16 active pricing records. Missing/inactive vendor, missing policy, missing vehicle/category coverage, ambiguous selectors, invalid monetary values, reversed effective dates, or unsupported CESS blocks completion.

1. Obtain documented business approval for issuer/commercial structure and each applicable vehicle/category GST rate and CESS decision. An explicit zero CESS decision is required if zero applies; the system does not choose zero. Nonzero CESS remains unsupported by the existing calculation/invoice implementation and cannot be activated through this workflow.
2. A SUPER_ADMIN can now enter the complete approved profile through admin `/pricing/approvals`, which calls `PUT /api/v1/admin/billing-approval/vendors/:vendorId/tax-profile` with `reviewHash`, `profile`, `decisionsConfirmed=true` and `businessApprovalReference`. Saving is validated, scoped to the vendor, audited atomically, and leaves the gate pending. The older direct database-writing command is retired; use this authenticated and audited UI/API. No live installation was performed during this work.
3. Use an authenticated **SUPER_ADMIN** session to request `GET /api/v1/admin/billing-approval`. This private, no-store endpoint returns the pending configuration, vendor profiles, current car/pricing scope, a blocker if validation fails, and `reviewHash`. Review the actual monetary values, scope, issuer identity, policy version, tax decisions, and effective dates against the approval documents. Do not log or share the full response; it may include private billing information.
4. Resolve any blocker through authorized fleet/profile workflows, then obtain a fresh review. Fleet rental-price create/update APIs require `fleet.update`; ordinary vendor verification does not approve tax policies.
5. Submit `POST /api/v1/admin/billing-approval/complete` with exactly these fields:
   - `reviewHash`: unchanged value from the reviewed GET response.
   - `idempotencyKey`: a new UUID for this approval operation; retain it for retries.
   - `rateConfirmed`, `cessConfirmed`, `taxConfirmed`, `globalScopeConfirmed`: each explicitly `true` after review.
   - `rateApprovalReference`, `cessApprovalReference`, `commercialStructureApprovalReference`: nonblank approval-document references, each at most 500 characters. References record the accountable human decision; the server cannot establish their legal validity.
6. Completion re-reads the entire scope in a serializable transaction, validates it, and compares the review hash. It atomically changes the pending status to `APPROVED`, retains the historical configuration and private/inactive flags, appends an approval receipt, and writes `AuditLog` with the authenticated actor, references, review hash, timestamp, car/pricing IDs and prior status. It does not change prices, vendor profiles, customer data, or the quote implementation. The historical nullable global rate fields remain historical; actual approved rates come from the vendor profile.
7. Retry an ambiguous network result with the identical body and idempotency key. The same actor/body returns the original approval ID without a second audit. Different input/actor using that key returns `409 IDEMPOTENCY_CONFLICT`. A stale review or serialization conflict returns `409 BILLING_REVIEW_STALE`: fetch and review again before a new approval attempt. Audit failure rolls back completion.

All endpoints use existing DB-backed authentication and role resolution. CUSTOMER, VENDOR and PLATFORM_ADMIN do not receive this global completion authority. No role grants or database migrations were added. The admin `/pricing/approvals` placeholder has now been replaced with policy entry, quote readiness, commercial review, audit records, explicit confirmations and a final confirmation dialog. See the [complete field checklist and operations guide](../../rentcar-admin/docs/PRICING-APPROVAL-OPERATIONS.md).

GET review now returns structured `readiness` blockers and the latest 20 relevant audit entries. Readiness is for billing configuration only. Completion receipts include `scopeHash`; changes to the approved fleet/vendor/pricing scope produce `STALE_REVIEW`. This is diagnostic only and does not change the customer quote gate.

## Business limitations that remain

- This is a one-time completion for the existing pending gate, not a general policy editor or scheduled tax-policy system. Profiles currently have a version and explicit approval flags but no tax effective-from/to fields. Rental pricing has its existing nullable effective dates; validation respects unbounded endpoints and requires ordered bounded endpoints.
- Later inventory/policy changes still use existing workflows; this API does not add ongoing tax-policy governance. Such changes require renewed operator review. The existing quote service's development fallback for vendors without a policy remains unchanged.
- A configured policy requires authenticated customer billing before quote creation. The exact original **guest** quote will subsequently return `CUSTOMER_BILLING_REQUIRED`, not necessarily 201. Authenticate legitimately, preserve the same car/trip, provide the required recipient registration/address configuration, and regenerate the quote. Do not bypass this second prerequisite to force the desired journey order.
- Test fixtures verify local behavior only. Successful authorization/approval, concurrent transactions, and rollback must still be exercised in a dedicated real-database test environment using approved policies and authorized accounts before claiming production readiness.
